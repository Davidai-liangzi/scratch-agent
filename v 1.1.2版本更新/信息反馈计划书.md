# v1.1.2 版本更新计划书（新批：信息反馈）

> 本批新增「问题反馈」功能：用户在软件里写一段话，一键送到开发者的接收端。
> 结论先说：**可行性高**，代码量很小；真正的成本不在写代码，而在「接收端选型」和「隐私边界」。

## 一、更新目标

| 编号 | 目标 | 一句话描述 |
|---|---|---|
| ① | 反馈入口 | 设置对话框里加「问题反馈」，弹出填写窗 |
| ② | 一键送达 | 点「发送」把内容发到接收地址，成功/失败都有明确结果 |
| ③ | 自动附带 | 可选带上版本、系统信息、脱敏日志，方便定位问题 |
| ④ | 绝不泄密 | `config.json` 里的 API Key **任何情况下都不离开客户端** |
| ⑤ | 离线可用 | 没配地址 / 网络不通 / 被接收端拒收 → 自动存本地文件，不丢内容 |

## 二、可行性结论

**技术上没有任何拦路的地方。** 需要说清的是三件事：

1. **用户侧零门槛**：接收地址就是一个 HTTPS 收件口，用户那端只发生「一次 HTTP POST」。
   他不用加群、不用装飞书/钉钉、不知道群的存在、也不需要有账号。
2. **开发者侧只要一条 URL**：见 §3.2 的三步准备，五分钟搞定，免费。
3. **唯一确定的隐患**：地址内置在 exe 里，可被逆出来用于刷你的群。客户端限流只能防手滑，
   **真正的防线在接收端**（见 §3.5）。

### 已排除的方案

| 方案 | 为什么不用 |
|---|---|
| GitHub Issues API | Token 内置客户端 = 高危（能被拿去做破坏性操作）；且国内网络常不通 |
| SMTP 直发邮件 | 邮箱凭据同样内置，且极易被判垃圾邮件 |
| `mailto:` 唤起邮件客户端 | 要用户自己点「发送」，送达率低；保留为线下兜底手段 |

## 三、设计

### 3.1 链路

```
用户软件 ──HTTPS POST(JSON)──> 接收地址 ──> 你的群 / 你的服务
   │
   └─ 发不出去 ──> 反馈/feedback_*.txt（本地文件，提示用户手动转交）
```

### 3.2 接收端（可配置）

地址来源，**前者优先**：

1. `config.json` 的 `feedback_webhook` —— 不改代码就能换地址；
2. [`core/feedback.py`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L31) 的 `DEFAULT_WEBHOOK` —— 发版前填。

按域名自动挑 JSON 结构（[`_payload()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L113-L123)）：

| 接收端 | 结构 |
|---|---|
| 飞书 `open.feishu.cn` | `{"msg_type":"text","content":{"text":…}}` |
| 钉钉 `oapi.dingtalk.com` | `{"msgtype":"text","text":{"content":…}}` |
| 企微 `qyapi.weixin.qq.com` | `{"msgtype":"text","text":{"content":…}}` |
| 其他（Worker / BaaS / 自建） | `{"text":…, "context":{…}}` |

#### 飞书配置（逐步）

全部操作都在**你自己的飞书**里完成，与用户无关（参考[飞书官方文档](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)）。

1. **建群**：新建一个群聊，名字随意（如「ScratchGenerator 反馈」）。只有自己一个人也够用 ——
   它的作用只是当你的收件箱。
2. **加机器人**：进入这个群 → 右上角「···」→ **设置** → **群机器人** → **添加机器人** →
   选 **自定义机器人** → 填头像/名称/描述 → **添加**。
3. **拿地址**：添加后会直接给出 webhook，**复制它，然后点「完成」**：

   ```
   https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxxxxxxxxxxx
   ```

4. **配安全设置**（第 3 步之后、或事后点群里机器人头像进详情页）：见下表 —— **这一步选错会直接发不出去**。
5. **填进程序**：见本节末尾。

**三个安全设置怎么选**：

| 选项 | 选不选 | 原因 |
|---|---|---|
| **自定义关键词** | ✅ **选它** | 最简单、零成本。关键词填 `ScratchGenerator`（最多可设 10 个、回车分隔）。我们的正文固定以 `【ScratchGenerator 反馈】` 开头，天然命中 |
| IP 白名单 | ❌ 不要选 | 用户 IP 不固定，开了等于把所有人都挡在门外，返回 `19022 Ip Not Allowed` |
| 签名校验 | ❌ 不要选 | 我们**没有实现签名**（要靠 `timestamp + 密钥` 做 HmacSHA256）。开了会返回 `19021 sign match fail` |

> 关键词只对 `text` / `title` 这类文本参数生效 —— 我们发的正是文本消息，所以有效。

**常见返回码对照**（飞书**即使拒收，HTTP 状态码通常也是 200**，所以必须看响应体）：

| `code` | 含义 | 我们的处理 |
|---|---|---|
| `0` | 成功 | 判定送达 |
| `19024` | `Key Words Not Found`（关键词没命中） | 自动转本地文件兜底 |
| `19022` | `Ip Not Allowed`（不在 IP 白名单） | 同上 |
| `19021` | `sign match fail`（签名/时间戳不对） | 同上 |
| `9499` | `Bad Request`（请求体格式错或**超过 20 KB**） | 同上 |

**填到哪里**（两选一）：

| 位置 | 放什么 | 效果 |
|---|---|---|
| [`core/feedback.py`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L34) 的 `DEFAULT_WEBHOOK` | **Worker 中转地址**（可公开） | 写死进包里发版用；改了要重新打包 |
| 应用目录下 `config.json` 加 `"feedback_webhook"` | 同上（排障时临时覆盖） | **不用改代码、不用重新打包**；点「保存设置」不会把它冲掉 |

> **真正的群机器人地址不要放这两处** —— 它只存在 Worker 的环境变量 `FEISHU_HOOK` 里（见下一节）。

**钉钉的坑**：安全设置若选了「自定义关键词」，消息里必须含关键词。
正文开头固定写 `【ScratchGenerator 反馈】`（[`build_body()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L124-L146)），正好当关键词用。

#### 中转层：Cloudflare Worker（推荐 · 本批采用）

**为什么需要它 —— 客户端里能藏住的秘密为零：**

- 关键词必须是正文里的固定串，而正文格式就在客户端代码里 → 源码一公开，关键词跟着公开；
- 签名校验的密钥同样在客户端 → 一样藏不住；
- 而地址**又必须**烤进客户端：发布 ZIP 里刻意不含 `config.json`（避免把你本机的 API Key 一起发出去），
  所以放 `config.json` 的话新用户拿到手就是空配置，功能直接退化成「存本地」，所有人都收不到反馈。

结论：**客户端只放一个「可以公开」的中转地址**，真正的群机器人地址与限流都放在服务端。
这样地址即使被逆出来，刷到的也只是一个有限流的入口，**你的群刷不爆** —— 这是「泄露后仍可控」，
也正是它比关键词强的地方。

代码在 [`worker/feedback-proxy.js`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/worker/feedback-proxy.js)，
**不含任何秘密，可以随仓库一起公开**。

**部署步骤**（全程网页操作，免费额度 10 万次/天，不用服务器）：

1. 注册登录 Cloudflare → 左侧 **Workers & Pages** → **创建** → **Worker** → 起名（如 `sg-feedback`）→ 部署默认代码；
2. 进这个 Worker → **编辑代码** → 把 `feedback-proxy.js` 全文粘进去 → **部署**；
3. **加变量**：Worker → **设置** → **变量和机密** → 添加 `FEISHU_HOOK`，值填真正的飞书群机器人地址 → 保存；
4. **建 KV**（限流计数用）：左侧 **存储和数据库** → **KV** → 创建命名空间（如 `sg-feedback-rate`）；
5. **绑 KV**：回 Worker → **设置** → **绑定** → 添加 **KV 命名空间** → 变量名填 `RATE`、选中刚建的命名空间 → 保存；
6. **自测**：浏览器打开 Worker 地址（`https://sg-feedback.<你的子域>.workers.dev`），
   应看到 `{"code":0,…,"hook_configured":true,"rate_limit":true}` —— **两项都是 `true` 才算配齐**。

**限流规则**（代码顶部常量，可自行调）：

| 规则 | 值 | 作用 |
|---|---|---|
| 同一 IP | 3 次 / 分钟 | 挡单点连刷 |
| 全局 | 200 条 / 天 | 保底：就算被刷也刷不爆群 |
| 请求体 | ≤ 18000 字节 | 与客户端一致 |
| 正文 | ≤ 4500 字 | 再兜一道 |

**客户端要改什么：一行都不用改。** 把 Worker 地址填进 `DEFAULT_WEBHOOK` 即可 ——
因为 [`_payload()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L148-L158)
对非 IM 域名发的正是通用格式 `{"text":…,"context":{…}}`，Worker 读 `text` 再转发给飞书。
限流触发时 Worker 返回 HTTP 429，客户端**已有的**「非 200 → 存本地文件」分支直接生效。

> ### ⚠️ 重要发现：`*.workers.dev` 在国内被 DNS 污染
>
> Worker 用 `wrangler` 部署**成功**（`Uploaded` / `Deployed` / `Current Version ID` 都拿到了），
> 但实测国内**直连不可达**：
>
> ```
> sg-feedback.1696889557.workers.dev -> 185.60.216.50   ← Meta 的 IP，假的
> anything.workers.dev               -> 157.240.17.41   ← 也是 Meta
> workers.dev                        -> 80.87.199.46   ← 更离谱
> 对照 cloudflare.com                -> 104.16.132.229  ✅ TCP 通
> ```
>
> 这是 DNS 污染（返回假 IP），不是配置问题。**结论：靠 `workers.dev` 域名无法服务国内用户。**
>
> 要真正可用，需要二选一：
> - **绑自有域名**（推荐）：买域名 → 接入 Cloudflare → 给 Worker 加自定义域。
>   Cloudflare 的 anycast IP（`104.16.x.x`）国内实测可连，因此这条能通。
> - **换国内 serverless**（腾讯云函数 / 阿里云 FC）做同一件事。
>
> 客户端代码**两种都不需要改** —— 只换一个地址。
>
> 另：`workers.dev` 在**开着代理**时是通的（本机实测 HTTP 200），所以它本身没坏，
> 只是国内裸网到不了。这也意味着**不能用带代理的验证结果去推断用户环境**。
>
> **本批决定（经确认）**：中转层**暂缓**，先走「直连飞书 + 自定义关键词」。
> Worker 与 KV 已在 Cloudflare 建好、验证通过，**原地保留**；
> 将来要么给它挂自有域名（几十一年的 `.cn`/`.top`），要么改用国内 serverless，
> 届时**只换 `DEFAULT_WEBHOOK` 一行**，客户端其余代码一个字都不动。

### 3.3 隐私红线

`config.json` 里存着用户**真实的 API Key**，这是本功能最大的风险点。对策是「白名单 + 统一脱敏」：

- **只发白名单内容**：用户手写正文 + 程序版本 + 系统/Python 版本 + 厂商名 + 档位名。
  这四项都**不含 Key**；配置文件的其它字段一个都不发。
- **所有出站文本统一过 [`_scrub()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L62-L75)**，正文和日志都过：
  1. 替换掉用户已配的那几把 Key（精确串匹配，长 Key 先替，避免短的先吃掉长的）；
  2. 替换掉接收地址本身；
  3. 正则兜底：`sk-` 前缀 Key、`api_key=xxx` 这类赋值、以及任何 40 位以上的长 token。
- **日志默认不附带**（复选框默认不勾），只有用户主动勾了才读最后 200 行，且先过 `_scrub()`。

### 3.4 降级路径

| 情况 | 行为 |
|---|---|
| 未配置接收地址 | 不发起任何网络请求，直接存本地文件 |
| 请求异常（超时/连不上） | 存本地文件，提示原因 |
| HTTP 非 200 | 存本地文件，提示状态码 |
| HTTP 200 但响应体 `code`/`errcode` ≠ 0 | 存本地文件（飞书/钉钉/企微**拒收时 HTTP 也是 200**，必须看响应体） |

兜底文件落在 `反馈/feedback_YYYYmmdd_HHMMSS.txt`（[`_save_local()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L125-L137)），
对话框里给出路径并提供「打开所在文件夹」，不让用户白写一段话。

### 3.5 频率与长度

| 项 | 值 | 说明 |
|---|---|---|
| 正文长度上限 | 4000 字 | 防手滑贴长文 / 被当刷子 |
| **整条消息字节上限** | **18000 字节** | 飞书限请求体 ≤ 20 KB，留 2 KB 给 JSON 外壳 |
| 同进程最小发送间隔 | 30 秒 | 仅本进程内有效 |
| 请求超时 | 8 秒 | 弱网下不至于把用户卡住 |

**字节上限这一条是补上的（原实现有坑）**：飞书官方明确「请求体大小不能超过 20 KB」，
超了返回 `9499 Bad Request`。而原实现把最多 200 行日志全量拼进去，中文 UTF-8 是 3 字节/字，
很容易撞线。另外 `requests` 的 `json=` 参数默认 `ensure_ascii=True`，中文会被转义成 `\uXXXX`
（**6 字节/字**），体积还要再翻一倍。

两处都改了：

- 发送时改为自己 `json.dumps(..., ensure_ascii=False).encode("utf-8")` 并显式带
  `Content-Type: application/json`，中文按 3 字节算，体积可控；
- [`build_body()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L122-L138)
  加了字节预算：正文按用户写的算，**日志「能塞多少塞多少」**（[`_clip_tail()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L111-L119)
  只保留最后能装下的部分）；万一正文本身就顶破上限，则由
  [`_clip_head()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/feedback.py#L101-L108)
  从尾部截断并标注「已截断」。
  两个截断函数的**提示语自身也计入预算**（第一版漏算了，实测超 34 字节，已修）。

> **诚实说明**：客户端限流挡不住「把 URL 逆出来用脚本刷」。真要防，得在接收端做——
> 中间套一个 Cloudflare Worker，做频率限制、长度校验、来源校验，再转发到群。
> 这属于可选的第二步，**不是必须**：一开始就用群机器人地址也已经能收反馈。
>
> 飞书侧真实限流：单租户单机器人 **100 次/分钟、5 次/秒**，且建议避开整点/半点
> （系统压力大会返回 `11232` 限流错误）。正常反馈量离这些阈值很远。

### 8.1 背景与约定

用户反馈「问题反馈…」「浏览…」后面的省略号没必要。先说清它不是手滑：

> **「按钮标签 + …」是一条老约定**（Windows 桌面时代）：表示**点了不会立刻完成，还会弹窗
> 要你再选/再填**。按这个约定——`浏览…` 弹文件选择框、`问题反馈…` 弹反馈对话框，
> 两者其实都**合乎约定**。但这套约定现代 App（尤其国内）多已弃用，属纯观感问题。

**所以决策点不是"对不对"，而是"要不要统一"** —— 全项目共 4 处用了它，
只改用户点名的 2 处会造成同一 App 内不一致，因此**一次改完 4 处**。
