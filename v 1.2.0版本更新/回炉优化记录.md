# 回炉优化记录（D + C）

> **一句话**：把两次真实踩过的语法坑写进语法表（D），并要求修复轮「一次改完所有列出的问题」（C）。
> 两处都是提示词层面的最小修改，**不新增任何检查逻辑**，目标是减少回炉次数。

## 一、背景：回炉已经是最大的单项成本

用例集基线实测（tour）：**一次回炉 ≈ +10k token**。

| 用例 | 回炉 | token |
|---|---|---|
| tour（P1 阶段） | 1 | 42,667 |
| tour（A 方案阶段） | 2 | 62,334 |

而这两次回炉的根因**都不是模型能力不足，而是提示词没说清**：

| 触发 | fractch 报错 | 根因 |
|---|---|---|
| `change_x -meteor_speed;` | `expected a number but found 'm'` | 语法表只写了 `change_x 10`，没写「只能是字面量」 |
| `setrotationstyle(STYLE: "left-right");` | `unknown block 'setrotationstyle'` | 语法表给了 `motion.setrotationstyle(...)`，但没强调「必须带前缀」 |
| tour 第 1 轮同时报了「缺声明」和「没切换」 | — | 模型只修了前者，于是又触发第 2 轮 |

## 二、D：语法表补两条

**改动位置**：[core/prompts.py](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/prompts.py) 的 `_SYSTEM_PROMPT_CORE`【FRACTCH 语法】

| 位置 | 新增内容 |
|---|---|
| `▲ 运动` 段 | `move / turn / change_x / change_y` 后面**只能跟数字字面量**；写 `change_x -速度` 这类变量或算式会直接报语法错（`expected a number`）；需要按变量改位置时，用 `if/else` 分档写不同字面量 |
| `▲ 语法要点` 段 | 带参数的运动积木**必须带 `motion.` 前缀**（`motion.setrotationstyle(...)` / `motion.pointtowards(...)` / `motion.glidesecstoxy(...)`）；裸写 `setrotationstyle(...)` 会被当成未知积木 |

## 三、C：修复提示词「一次修完」

**改动位置**：`REPAIR_PROMPT` 与 `REPAIR_PROMPT_FULL` 各加一行

> 报错可能有多条，**请一次把所有列出的问题全部改完**（不要只修第一条、也不要只修一部分），否则会再触发一轮修复。

与已有的「最小改动」约束不冲突，二者是互补的：

- **改得少** —— 不要顺手重构没问题的部分（防止改坏）；
- **但要一次改全** —— 报错列表里的每一条都要落实（防止白跑一轮）。

## 五、效果怎么量

- **指标**：同一用例集的「回炉次数」与「总 token」
- **对照**：tour 当前 2 次回炉 / 62,334 token
- **预期**：
  1. `change_x 变量` 与裸写 `setrotationstyle` 这两类语法错不再触发回炉；
  2. 同时报多个问题时，回炉次数从 2 → 1。
- **时机**：建议等 A（交互冒烟）与 B（回炉只发相关文件）都落定后，用全量基线一次性验证，
  避免每改一项就烧一轮 token。

## 六、B：回炉只发与报错相关的文件

**改动位置**：`core/project.py` 新增 `_repair_files()`，`_repair_messages()` 改用它裁剪输入。

规则（保守优先，宁可多发，也不让模型缺上下文改坏别处）：

| 情况 | 行为 |
|---|---|
| 报错里出现文件路径（`Guide/main.fractch:6: ...`） | 只发这些文件 + `Stage/main.fractch` |
| 报错没提任何文件（如「大纲契约」这类项目级问题） | 原样全发 |
| 报错提到的路径不在清单里（例如已被重建删除） | 退化为全发 |
| 裁完不足 2 个、或几乎等于全量 | 全发 |

裁剪时会在文件清单前加一句：「只列出与报错相关的文件；没有列出的文件保持原样，请不要凭空重写。」

**为什么裁**：一次回炉 ≈ +10k token，其中文件清单占 3~4k，是唯一可压缩的输入部分。

**验证（合成用例）**：

```
两个文件报错        → 3/5 个（两个报错文件 + Stage）
项目级报错（无路径） → 5/5 个（全发）
报错提到全部文件     → 5/5 个（全发）
请求体长度           → 2342 字符（全量时 3286），单轮减少约 29%
```

**预期收益**：单轮回炉省 **15%~20%** 输入 token——不是翻倍级，因为 system 提示词（固定约 3k）和模型输出（2~3k）不可压缩。
**风险**：模型看不到未列出的文件，可能改出跨文件问题（例如广播发了没人收）。这类会被规则 2「广播有发有收」抓回来，等于"用一轮换省下的 token"，所以策略保持保守。

## 七、自动补造型声明（免回炉）

**触发场景（2026-10-19 全量基线的真实案例）**：tour 里 `Guide` / `Visitor` 两个角色
**把 SVG 画好写进了 `assets/`，却完全没写 `costume` 声明**。fractch 会补一个默认空造型，
角色在舞台上完全隐形、也点不到，而语法检查不报错。以前只能回炉让模型补 —— 一次约 1 万 token。

**改动位置**：`core/assets.py` 新增 `inject_missing_sprite_costumes()`，
在生成流程「素材写入磁盘之后、工程检查之前」调用（`core/project.py`）。

规则：

| 情况 | 行为 |
|---|---|
| 目录里有 `.svg` / `.png`，但 `.fractch` 里**一条声明都没有** | 按文件名补声明 |
| 已有任意一条声明 | **一个字都不改**（避免覆盖模型的选择） |
| 目录里没有素材文件 | 跳过（交给 `_rule_missing_costume` 报给模型画） |
| Stage | 补 `backdrop`；普通角色补 `costume` |

旋转中心取图片的半个宽高：PNG 读 IHDR，SVG 读 `width/height` 或 `viewBox`。

**验证**：

```
Hero（120×80，无声明）      → 补 costume "hero" ... center 60,40;    ✅
Stage（480×360 PNG，无声明） → 补 backdrop "bg" ... center 240,180;   ✅
Cat（已有声明）             → 内容完全未变                            ✅
Ghost（没有素材）           → 不处理                                  ✅
第二次运行                  → 返回 []，无重复插入（幂等）             ✅
6 个真实工程                → 全部返回 []（零副作用）                 ✅
补完后跑 fractch check      → []（补出来的语法合法）                  ✅
compileall / test_fallback_vm.py → 通过                              ✅
```

**与 lint 的分工**：`_rule_missing_costume` 继续保留作兜底 —— 当角色连素材文件都没有时，
只能让模型补画；有素材只是忘了声明的情况，从此由这一步机械解决，不再消耗回炉。

## 八、明确没有做的事

- 没有新增任何运行时/静态检查规则；
- 没有改动 lint 的规则集（仍是 7 条纯确定性规则）；
- 没有引入语义判定的启发式（题材是否匹配、台词与按键是否对应这类，误报成本远高于收益）。
