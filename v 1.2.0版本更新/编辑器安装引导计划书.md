# v1.1.2 版本更新计划书（新批：编辑器选择与安装引导）

> 一句话：用户没装能打开 `.sb3` 的编辑器时，不再只在日志里丢一句「打开失败」，
> 而是弹一个窗口，让他自己选途径 —— 装一个新的，或用已经有的打开。

3. 触发时机确定：**没装编辑器却要打开时弹**；**设置里另加一个常驻入口**
4. 候选清单：确认按下表来

## 二、调查（先查再做，不猜）

### 2.1 一个被忽略的事实：本机早就装了，程序却一直认不出来

实测（`Get-AppxPackage` / `Get-StartApps`）：

| 应用 | 包名 | AUMID |
|---|---|---|
| TurboWarp | `45747ThomasWeber.TurboWarpDesktop_1.16.0.0_x64` | `45747ThomasWeber.TurboWarpDesktop_dx91esefr5w5e!TurboWarp` |
| Scratch 3 | `ScratchFoundation.ScratchDesktop_3.32.1.0_x64` | `ScratchFoundation.ScratchDesktop_wmbdy4q6dbx4t!ScratchFoundation.ScratchDesktop` |

旧的 `detect_turbowarp()` 只查 3 个固定路径（`%LOCALAPPDATA%\Programs\TurboWarp\` 等），
而**商店版装在 `Program Files\WindowsApps\`** —— 永远查不到。结果：明明装了，
程序却当作"没装"，只能靠系统文件关联碰运气。**这是本次顺带修掉的真 bug。**

### 2.2 下载渠道实测（关键数据，别当"应该还行"）

| 渠道 | 实测 |
|---|---|
| 国内 CDN（对照，排除"带宽慢"的干扰） | **2578 KB/s** |
| GitHub 资产（TurboWarp / Bilup 的官网安装包都在这） | **51 KB/s** |
| 微软商店 | 商店 ID 已用 `winget search --source msstore` 逐个核实；**速度未实测** |

- TurboWarp 安装包 **147.1 MB**，按 51 KB/s ≈ **50 分钟** → 官网下载这条路只能当兜底；
- `winget` 的社区源 `GarboMuffin.TurboWarp` **同样指向 GitHub 资产**，一样慢 → 不用它；
- 两者差 50 倍，**说明不是用户带宽问题，是 GitHub 资产在国内被限速**。

> 微软商店走微软自己的 CDN，通常是快的 —— 但**没实际装过就不算验证过**，
> 所以设计上刻意不依赖它（见 §3 的降级链）。

### 2.4 为什么**不**做「应用内播放器」

我一度提议：项目里已自带 `scratch-vm` / `scratch-render`，且实测 **WebGL 在 QtWebEngine 里可用**
（ANGLE + D3D11），可以做成应用内试玩、零安装。但用户指出关键一点：

> 只能看效果的话，细微的改动（自己能改的那种）可能非常不方便。

**采纳，撤回该方案** —— 只读播放器满足不了"学生想自己改积木"，反而不如让他用真编辑器。

> 附带发现（记下来备用）：`scratch-vm` / `scratch-render` / `scratch-storage` /
> `scratch-svg-renderer` 的**浏览器版 bundle 都在** `vm-runner/node_modules/*/dist/web/`，
> 连 `scratch-audio` 也在。将来若真要做内嵌预览，材料是齐的。

## 三、设计

**触发**（两条）：

1. **打开失败时自动弹**：`launcher.open_sb3()` 既找不到编辑器、`os.startfile` 也失败
   → 回调 GUI 弹窗（见 §4 的线程说明）；
2. **常驻入口**：设置 → 「编辑器」行 → 「选择 / 安装编辑器」。

**对话框分区**（`EditorDialog`）：

| 分区 | 内容 |
|---|---|
| ① 已检测到 | 列出探测到的编辑器（含商店版）+「用系统默认关联的程序打开」 |
| ② 一键安装 | TurboWarp / Scratch / Bilup 各一行 `[从微软商店安装]` |
| ③ 官网下载 | 三个官网按钮 + **如实标注慢**（51 KB/s、147 MB ≈ 50 分钟） |
| ④ 免安装网页版 | TurboWarp 网页版（**是完整编辑器，能改积木**） |
| ⑤ 手动指定程序 | 浏览选任意 exe —— **覆盖其余所有魔改版，不用穷举** |
| ⑥ 重新检测 | 装完点一下刷新 |

**三层降级，保证不会"只有一条路、走不通就死"**：

1. `winget install --source msstore` 一键装；
2. winget 不可用 → `ms-windows-store://pdp/?ProductId=…` 打开商店页，用户点「获取」；
3. 商店也打不开 → 官网下载 / 网页版 / 手动指定，三条各自独立可用。

## 四、实现

| 文件 | 改动 |
|---|---|
| [`core/editors.py`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/editors.py) | **新增**：候选清单、探测（目录扫描 + 开始菜单）、winget 安装（流式输出）、商店页 / 网页版跳转 |
| [`core/launcher.py`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/launcher.py) | `open_sb3` 改为**先自动探测再打开**、返回 `opened`/`no_editor`；新增 `NO_EDITOR_HOOK`、`activate_store_aumid`、`open_with_target` |
| [`gui.py`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/gui.py) | **新增** `EditorDialog`；设置加「选择 / 安装编辑器」；注册 hook + `_pump_ui_queue` 加 `no_editor` 分支 |

**几个刻意的设计决定：**

- **探测不猜 exe 文件名**：不硬编码 `TurboWarp.exe` / `Bilup.exe`，而是扫安装目录、挑一个
  不像卸载器/更新器的 exe（`_BAD_EXE` 过滤）。各家改名/改版都不影响。
- **开始菜单必须精确匹配**：用 `in` 这种模糊匹配的话，「Scratch Link」「Scratch少儿编程」
  都会被当成官方 Scratch —— 那会让程序**主动启动一个不相干的程序**。所以用精确别名表。
  这条专门写了测试。
- **线程安全**：`NO_EDITOR_HOOK` 可能在**工作线程**里被调用（生成后自动打开走的是后台线程），
  所以它只往 `_ui_queue` 丢一条 `("no_editor", path)`，由主线程的 `_pump_ui_queue` 弹窗 ——
  延续 BUG-08 的教训：工作线程绝不碰 Qt 对象。
- **`open_sb3` 返回值从 `None` 改成字符串**：调用方都不用它，向后兼容无风险。

## 七、补丁：区分「这个编辑器到底能不能带文件启动」

### 7.1 问题（用户指出）

> 编辑器支持自动打开文件的不多，我记得原版 scratch 是不行的

用户说得对，而且这暴露了我实现里的一个**假成功**：`Popen([exe, path])` 只要能启动就返回成功、
打印「已用 X 打开」—— 但编辑器完全可能**忽略那个路径参数**，用户对着一个空编辑器，
而我们还以为一切正常。

### 7.2 核实结果

| 编辑器 | 能否带文件启动 | 依据 |
|---|---|---|
| **TurboWarp** | ✅ 能 | 官方更新日志：「Added file association for sb3 files (lets you double click files to open)」 |
| **官方 Scratch** | ❌ 不能 | MIT 帮助中心原话：*"Double-clicking on a Scratch Project from your operating system won't open in Scratch Desktop as you might expect."* 必须先开软件，再 File → Load from your computer |
| **Bilup** | 推断能（未实测） | 官网安装页与 TurboWarp 几乎一字不差，同源；所以标记为「能」—— 万一它不收参数，表现只是打开一个空编辑器，有提示兜着 |

### 7.3 改法：宁可说"要手动载入"，也不谎报"已打开"

1. 候选清单每项加 `opens_file` 能力标记（见 [core/editors.py](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/editors.py#L24-L65)），
   探测结果把它带出来；
2. [`open_with_target()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/launcher.py#L124-L150)
   返回值由 `bool` 改成 `"opened"` / `"manual"` / `"failed"`：
   - 支持的 → 照旧把 `.sb3` 传进去；
   - **不支持的 → 只启动程序（不塞参数），返回 `"manual"`，并打印文件路径 + 「文件 → 从电脑中加载」的指引**；
3. [`open_sb3()`](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/launcher.py#L153-L191)
   确定优先级：**支持的编辑器 → 系统文件关联（有些编辑器只靠关联、不吃命令行参数）→ 不支持的编辑器（manual）→ 弹窗引导**；
4. `EditorDialog` 里两种编辑器的文案分开：
   - 支持的 → 按钮「用它打开」，点了成功就关窗；
   - 不支持的 → 按钮**「打开编辑器（需手动载入）」**，列表里还标注「⚠️ 不支持自动载入项目」；
     点完不关窗，状态区**把完整文件路径摆出来**，并出现一个「**复制文件路径**」按钮。

**不看屏幕怎么验**：TurboWarp 是 Electron 应用，窗口标题会反映当前项目
（形如 `<项目名> - TurboWarp Desktop`）。用 Win32 `EnumWindows` + `GetWindowTextW`
枚举可见窗口读标题、激活前后对比 —— 这个手法排查下拉弹层时用过（§19），可靠。

```
第一次（从没有窗口开始）
  测试项目： bug03_final.sb3 (279421 字节)
  激活前标题： （没有已开着的窗口）
  激活返回：   opened
  8s/16s/26s 后标题： ['bug03_final - TurboWarp Desktop']

第二次（换项目，排除"标题碰巧"）
  换用项目： my_ai_game.sb3 (114475 字节)
  8s/16s 后标题： ['bug03_final - TurboWarp Desktop', 'my_ai_game - TurboWarp Desktop']
```

标题**跟着换的项目名走** → 确实载入了我们传进去的那个 `.sb3`，不是巧合。
所以 TurboWarp 的 `opens_file = True` 现在是**实测值**，不是推断。

## 十、修性能：设置 / 编辑器对话框打开慢

### 10.1 现象与定位（先量后改）

用户反馈：打开设置、打开编辑器选项都要等很久。先测，不猜：

| 环节 | 耗时 |
|---|---|
| `_list_start_apps()`（跑 PowerShell `Get-StartApps`） | **666 ms** |
| `detect_installed()` 冷 / 热（命中缓存） | **653 ms** / 2 ms |
| `SettingsDialog()` 冷缓存 | ≈ 650 ms |
| `EditorDialog()` | **650 ms，而且每次都是** |

两个根因：

1. **同步跑在 GUI 主线程**：探测要起一个 PowerShell 进程读开始菜单（约 0.7 秒），
   这段时间窗口根本不出现 —— 用户感觉就是"卡住了"；
2. **`EditorDialog._refresh()` 每次都 `clear_cache()`** —— 缓存等于白建，
   永远享受不到那 2 ms，所以**第二次打开一样慢**。

### 10.2 改法

| 改什么 | 怎么改 | 目的 |
|---|---|---|
| 编辑器对话框的探测 | 挪到后台线程（`_BgWorker`），先显示「正在检测已安装的编辑器…」，结果经队列回主线程渲染 | 窗口**立刻**出现 |
| 缓存 | 只有「重新检测」/ 刚装完 / 刚手动指定才清缓存 | 第二次打开走缓存（2 ms） |
| 设置窗口 | 去掉那里的全量探测，只留最便宜的 3 路径检查（`detect_turbowarp`，毫秒级） | 冷启动不再卡 |
| 子进程 | PowerShell / winget 一律加 `CREATE_NO_WINDOW` | 不再闪黑框 |
| 收尾 | 探测与安装**共用**同一个队列与轮询定时器 → 用 `_pending` 计数，**两个都跑完才停定时器** | 防止一个先结束把另一个的进度接收关掉 |
| 旧控件 | `_render_found()` 里对旧 holder 先 `hide()` 再 `deleteLater()` | `deleteLater` 是**延迟**销毁，不先隐藏会残留一帧 |

### 10.3 验证（13 项断言，失败 0）

| 项 | 改前 | 改后 |
|---|---|---|
| 设置窗口（冷缓存） | ≈ 650 ms | **3 ms** |
| 编辑器对话框（冷缓存） | 650 ms | **2 ms**（探测在后台跑） |
| 编辑器对话框（第二次打开） | 650 ms | **2 ms**（命中缓存） |
| 立刻出现「正在检测…」占位 | — | ✅ |
| 探测结果回填、占位被替换掉 | — | ✅ |
| **布局里自始至终只有一个块**（旧占位块确实被移除） | — | ✅ |
| 定时器无空转（`_pending` 归零后才停） | — | ✅ |
| 「重新检测」确实强制重建缓存 | — | ✅ |

> 断言里特意加了「布局里只有一个块」—— 防的就是旧占位块没清干净、和结果叠在一起显示。
