# v1.1.2 版本更新计划书（新批：首次交付质量）

> 本批目标：**让用户第一次拿到手的作品就近乎完美**。
> 结论先说：**继续往提示词里加规则走不通（有实证上限）**；正确的低成本路径是
> ——把「什么算合格」从提示词搬进代码，插进**已经存在**的回炉环。
> 四个动作全部落在既有钩子上：不新增机制、不新增依赖、不改架构。

## 一、目标与前提

### 1.1 目标必须拆成两件事

「第一次产出近乎完美」有两种读法，选错会导致整条路径走偏：

| 读法 | 含义 | 是否可达 |
|---|---|---|
| 甲：模型第一轮就写对 | 一次请求返回即正确 | **不可达**（有实证上限，见 §1.2） |
| 乙：**用户第一次拿到手的成品是对**的 | 允许内部自动修复，用户无感知 | **可达**，且骨架已具备 |

本计划按 **乙** 执行。依据：用户看不到中间过程——[project.py](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/project.py#L418-L533) 里的 `MAX_ATTEMPTS = 3`
与 `AUTO_FIX_ROUNDS = 1` 全部在后台跑完，用户只拿到最终的 `.sb3`。

### 1.2 为什么甲不可达（实证依据）

- **NL2Scratch**（arXiv:2606.22061，ETH Zurich，2026-06）：模型 token 级 F1 与解析成功率均 **> 0.93**，
  但「语义完全对齐」的样本**不到 18.9%**，且程序越长差距越大。
- 同文结论：错误**集中在动作、条件、数值参数这几类 slot**，而不是「不知道规则」。
  → 说明「继续加提示词条目」是负收益：规则已经够多，问题不在这里。

### 1.3 由此得到的设计原则

> **从「嘱咐模型」转向「程序验收」。**

### 动作 1：静态契约检查（覆盖最大、最确定）

- **改哪**：新建 `core/lint.py`，函数签名返回 `List[str]`；
  在 [check_project](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/core/fractch.py#L27-L42) 之后并入 issue 列表（它本来就返回 `list`，合并是一行的事）。
  报错自动进现有回炉环，无需改回炉逻辑。
- **只做这 5 条**（全部纯文本可判定，且正好命中研究点名的失效模式）：

| # | 检查 | 对应依据 |
|---|---|---|
| 1 | 同角色同款帽子积木重复（`when flag` / `when clicked` / `when key X` / `when broadcast X` 各最多一个） | 提示词【可靠性规则】6；判定完全确定 |
| 2 | `broadcast X` 无对应 `when broadcast X` 接收 | 自检清单第 6 条；ScratchEval 的「同步屏障」失效模式 |
| 3 | **游览类契约**：每个选项角色必须有 `when broadcast <选路消息> { hide; }` | 场景包已明写「三个选项必须一起消失」，是历史踩过的坑 |
| 4 | **游览类契约**：`playing` 被置 1 后必须存在写回初值的语句 | 提示词【可靠性规则】4；ScratchEval 的「状态初始化」典型 bug |
| 5 | `change xxx =` 这类非法自增写法 | 提示词语法表明确禁止 |

> ⚠️ **实施变更（2026-10-17）**：第 3、4 条（游览类契约）**已移除**。
> 原设计想把场景包从「文字建议」升级成「可执行验收」，但两次真实运行都在**答题类**项目上误报 ——
> 答题按钮同样满足「多个角色点一下 → 写同一个变量 → 广播同一条消息」，纯文本无法区分
> 「选路」与「判分反馈」。按本节「误报远贵于漏报」的原则移除，详见 §6.1「第三次全量基线」。
> 最终落地的是 5 条纯确定性规则（上表 1、2、5 + 素材声明 + 占位符残留）。
- ⚠️ **为什么只做 5 条不做 18 条**：误报的代价是**一整轮回炉**
  （重发 system + 全部文件 + 重新生成 + 再 check + 再打包），成本远高于漏报。
  这 5 条是「几乎不可能误报」的下限集；其余（死变量、坐标越界、台词与 `when key` 对应等）
  需先设计判据再逐步纳入。

## 四、明确不做的事（「改动最小」的另一半）

| 不做 | 理由 |
|---|---|
| 不加任何提示词规则条目 | 研究结论很硬：错误集中在 operational slot，不是「不知道规则」。已有 13 条自检 + 18 条规则，再堆会稀释注意力，属负收益 |
| 不做场景包 registry 重构 | 它服务「以后加题材」与素材目录按需注入（FEATURE_PLAN 的 ENH-04），对「首次完美」零贡献 |
| 不做回炉轮 token 裁剪 | 已论证收益有限：`manifest` 里的官方素材只是 `@official:` 占位符，裁不出多少；裁太狠还会让模型看不到广播接收方而改出新 bug |
| 大纲轮不做专用 system prompt | 只加一句「双模式」声明（修改提示词【输出格式】段）即可消除与 `files` schema 的冲突，且不破坏前缀缓存 |

## 五、天花板与前提（必须说清）

### 5.1 运行时检查的天花板

[run.js](file:///c:/Users/16968/PycharmProjects/WelcomeScreen/vm-runner/run.js) 是**纯无头 5 秒运行，不支持脚本化输入**——不能点击、不能按键。

- **能覆盖**：绿旗后自动发生的部分（开场、自动讲解、背景切换、自动移动）+ 异常（报错、静止、克隆泄漏、线程残留）。
- **覆盖不了**：「点下去之后才发生的逻辑」——选项角色被点后有没有一起消失、打地鼠能不能加分、按键有没有反应。

**这正是动作 1（静态契约）比动作 2 更重要的原因**：交互类 bug 只能靠静态契约兜，
而它恰好是研究点名的失效主因。若要让这类也进闭环，需改 `run.js` 支持事件注入——
**那才是不小的改动**，放到本轮之后再评估。

### 5.2 前提：先定义「什么算完美」

「近乎完美」必须先可判定，否则无法验证、也无法优化。
需要固化一个 **5~8 条需求的用例集**（打地鼠 / 购物中心游览 / 答题闯关 / 换背景 / 角色不动 …），
每轮记录四个数：

1. 回炉次数
2. 是否最终打包成功
3. `detect_runtime_issues` 报了什么
4. 总 token

`run.js` 已能给出可执行判据，因此这件事成本很低——但它决定后面所有改动能否被评价。
