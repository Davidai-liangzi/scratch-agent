# 架构优化

下面这份顺序，是从你项目当前的真实状态（DeepSeek 主生成、已成屎山、尚无自动化验证）出发，按依赖关系排列的。每一步都以前一步的产出为输入，不完成前一步，后一步的收益会大打折扣。核心原则只有一句：先把裁决权从 LLM 手里拿走，再谈自动化和多模型。

## 第 0 步：定架构——确定“用户感知一个产品，后端一条管线”

在写任何代码之前，先确定三件事：

- 用户入口只有一个：用户提交需求，接收作品，不感知模型数量、不选择路径。
- 主力生成器是 DeepSeek：它负责代码骨架、机制计划、积木注入。不要在这一步纠结换模型。
- 编排器持有质量政策：由你的后端代码（不是 LLM）决定一次生成走哪条验证路径、什么条件下熔断、什么条件下升级。

这一步的产出是一张管线草图：需求 → 机制计划 → 积木生成 → 确定性验证 → （可选）软性审查 → 入库/返回。每个环节标注“由谁执行”（LLM / 无头VM / 静态分析 / 视觉模型）。

## 第 1 步：装硬门控——让“能不能跑”由无头 VM 裁决

这是整个方案的地基，不依赖任何额外模型，单独就能把功能正确性的下限拉起来。

做什么：

- 接入一个无头 Scratch VM（scratch-unified-mcp 或 @donrx/scratch-judge），能加载 .sb3、按绿旗、逐帧步进、读取变量和线程状态、断言。
- 为每一类生成需求定义一组 must checks：无卡死、无不可达状态、核心变量按预期变化、克隆体在预期生命周期内消失、广播发送/接收成对存在。
- 把 DeepSeek 的“完成”定义改为：通过 must checks 才算完成。不通过时，把运行时的具体症状（哪条断言失败、第几帧、涉及哪个变量）作为反馈，触发定向修正。

验证标准：任意一次生成，如果 must checks 不通过，管线拒绝返回“已完成”。你人工抽查 10 个被拒绝的样本，确认它们确实存在功能缺陷。

为什么先做这个：没有这道门，后面所有自动化和多模型审查都建立在“LLM 自述完成”的沙子上。DeepSeek 自评的假阳性率已知偏高，而运行时断言是确定性的、可重放的。

## 第 2 步：建循环与熔断——让修正自动发生，但有边界

在第 1 步的门控之上，加循环控制。

做什么：

- 实现 must / should 两级检查：must 不通过则带着反馈重新生成，should 不通过则记录但不阻断。
- 设置最大循环次数和墙钟超时（熔断）。连续 N 轮 must 失败，管线停止重试，输出结构化失败报告（失败断言、症状、涉及切片）。
- 维护一个小型回归套件（覆盖计分、碰撞、克隆、广播等核心机制），每次管线变更后重放，防止“修 A 坏 B”。

验证标准：一个故意构造的缺陷需求，管线能在熔断前自动尝试修正，且失败报告能定位到具体症状，而不是“生成失败”四个字。

## 第 3 步：摸清屎山——自动生成依赖矩阵与重构候选清单

现在开始处理存量项目。不要先改代码，先让工具告诉你哪里可以安全地改。

做什么：

- 用 AST 工具（@thanh01.pmt/algorithm-judge-kit 或类似）对现有 .sb3 做静态扫描：识别重复积木序列、孤儿广播（发无收/收无发）、未被读取的全局变量写入、过深嵌套或过长单线程。
- 生成角色 × 广播 × 全局变量的依赖矩阵，标出每个切片的出向依赖。没有出向广播、不写共享变量的切片标记为叶子切片。
- 产出重构候选清单，按“叶子安全度 × 重复度 × 历史变更频率”排序。

验证标准：清单中的每个候选切片，你人工确认它确实是一个可独立验证的模块边界。

## 第 4 步：锁行为——为候选切片生成特征化契约

在改任何切片之前，先锁定它当前的实际行为。

做什么：

- 对每个候选切片，在未修改的旧实现上运行无头 VM，录制可观察状态轨迹（变量值、线程状态、克隆体存活标志）作为行为快照。
- 将快照转化为可重放的断言脚本（特征化测试）：不判断“对不对”，只判断“改完之后是否和改之前一致”。
- 旧实现必须先通过自身的契约——这是安全网生效的前提。

验证标准：对一个切片做一次故意的错误修改，契约能自动捕获差异并拒绝。

## 第 5 步：绞杀式重构——从叶子开始，新旧并行，逐片替换

做什么：

- 按候选清单顺序，每次只处理一个切片。
- 为切片写 Spec（输入、输出、修改哪些变量、发送/接收哪些广播、触发条件），交给 DeepSeek 按 Spec 生成新实现，而不是在旧积木上自由发挥。
- 新旧并行：在同一组行为契约下分别运行，逐帧比对可观察状态。一致才切换；不一致则回滚，并把失败症状写入谱系记忆。
- 切换后保留旧积木作为“影子”一段时间，经过足够多次回归运行确认稳定后再删除。

验证标准：每完成一个切片，回归套件全绿，且该切片的重复度/依赖复杂度指标不劣于重构前。

## 第 6 步：上棘轮——防止重构完又长回去

做什么：

- 每次成功重构后，将当前的契约通过集、重复度指标、依赖矩阵叶子比例冻结为新的基线。
- 后续任何提交（无论人工还是 AI 生成），只能让这些指标不变或变好，不能变差。
- 把腐化检测（重复序列、孤儿广播、未读变量写入）嵌入管线，提交时自动标记。

验证标准：故意提交一个引入新重复积木的变更，棘轮门控拒绝它。

## 第 7 步：闭环自动化——让编排器驱动整条管线

前六步的每个环节都已可独立运行后，用一个编排器把它们串起来：

做什么：

- 编排器按“叶子安全度 × 重复度 × 变更频率”自动选择下一个切片。
- 自动执行：静态扫描 → 行为快照 → DeepSeek 按 Spec 生成 → 并行验证 → 通过则更新棘轮，失败则回滚并记录。
- 熔断时输出结构化失败报告，升级给人或升级到更强的推理预算。
- 参考 vibekit 的 /ralph-loop 式预算约束循环：自动重跑直到门控满足，但门控本身不可绕过。

验证标准：在无人干预的情况下，管线能连续完成 N 个切片的“扫描→重构→验证→棘轮”循环，且回归套件始终保持全绿。

## 第 8 步：选择性引入异构模型——只填补确定性检查的盲区

这一步放在最后，因为只有当前面的确定性门控已经可靠时，异构模型的多样性收益才能被安全收割。引入三个角色，全部在后端、用户无感知、按触发条件调用：

**角色一：补丁验证者（优先级最高）。**
选一个与 DeepSeek 不同家族的中国模型（Qwen3 系列或 Kimi K2），配置为只读、低频，只在硬门控全部通过之后、入库之前触发。它只接收执行产物（diff、断言通过清单、运行时轨迹摘要），不接收 DeepSeek 的生成推理，回答：“这段变更是否引入了确定性检查覆盖不到的风险？” 记录它的否决率与人工复核一致率，用数据决定是否保留。

**角色二：视觉审查者（按需）。**
当确定性视觉代理指标（角色重叠面积、色彩多样性、帧间变化率）触发异常时，让一个多模态模型（Qwen 系多模态变体）只处理被标记的可疑样本，做归因分析。不要让视觉模型扫描每一张截图。它的输出只是修正建议，最终仍由 DeepSeek 执行修正、由确定性指标再次验证。

**角色三：异构候选生成器（熔断后）。**
当某个切片连续多轮硬门控失败、熔断触发时，让异构模型（Kimi K2 或 Qwen3-Coder）独立生成一份候选重构，与 DeepSeek 的候选一同交给确定性门控裁决。谁通过用谁，都不通过则升级给人。这不是让用户选模型，而是在管线内部用异构生成打破 DeepSeek 在特定模式上的重复失败。

验证标准：每个异构角色都有明确的触发条件、成本上限和人工复核一致率记录。如果某个角色的否决与人工判断一致率低于阈值，关掉它。

## 依赖关系总览

```text
第0步 定架构
  └→ 第1步 硬门控（无头VM + must checks）
       └→ 第2步 循环与熔断
            └→ 第3步 静态扫描 + 依赖矩阵
                 └→ 第4步 行为快照 + 特征化契约
                      └→ 第5步 绞杀式重构（逐切片）
                           └→ 第6步 棘轮防退化
                                └→ 第7步 编排器闭环自动化
                                     └→ 第8步 选择性异构模型
```

第 1 步和第 3 步可以并行启动：硬门控解决“新生成的质量下限”，静态扫描解决“存量屎山往哪改”。但第 5 步的重构必须等第 4 步的契约就绪，第 7 步的自动化必须等第 5、6 步的手动流程跑通至少一轮。

## 底线

从头开始的顺序，本质上是按“独立性来源的强度”排序：确定性运行时断言最强，静态分析次之，行为契约再次之，LLM 审查最弱。先把最强的独立性来源装进管线，让“不精美”和“功能缺陷”被一个不依赖 DeepSeek 判断的机制可靠地检测出来，自动化和多模型才有意义。每一步都独立可交付、可验证，不需要一次性理解整个屎山，也不需要一开始就决定用几个模型。
