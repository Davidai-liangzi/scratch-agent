# 高质量生成升级计划书（Premium Pipeline）

> 前置结论来自 2026-10-20 的全链路 A/B：素材单调已基本解决（Jaccard 0.405 → 0.091，角色造型 4.5 → 6.9），
> 但暴露出新的天花板——**一次成型、没有审稿、没看过画面、没真正试玩**。
> 本计划书讨论的是「在 token 预算放大 10 倍的前提下，怎么把生成质量从“能跑”推到“做得好”」。

---

## 一、现状瓶颈

| 环节 | 现状 | 造成的质量问题 |
| --- | --- | --- |
| 设计 | 只有命中关键词才先出大纲（`_is_complex`），否则直接开写 | 简单需求没有全局规划；长需求大纲也只是一段 JSON，不约束每一幕 |
| 编码 | 全部文件在一次调用里输出（约 1.7 万 completion token） | 前几幕细致、后几幕草率；文件越多越容易漏交互、漏收尾 |
| 素材 | 按标签做 MMR 召回，模型**没有见过素材图** | 素材“不重样”但未必“贴切”；风格可能混杂 |
| 台词 | storygen 模板句直接落进工程 | Distinct-2 0.593 → 0.405，措辞集中 |
| 校验 | `fractch check` + lint + 5 秒 VM | 只验证“能跑”，不验证“能玩”：胜负不可达、点了没反应都查不出 |
| 采样 | 单次生成，temperature 0.3 | 没有候选对比，抽到差的这次就是最终结果 |

一句话：现在把 token 加在提示词长度上，边际收益很低；应该加在**多阶段约束 + 多源反馈 + 候选挑选**上。

---

## 二、目标与非目标

### 目标

1. 同一需求连续生成 3 次，人工盲评「素材贴切 / 画面协调 / 编排完整 / 内容趣味」均 ≥ 4/5。
2. 自动指标：台词 Distinct-2 ≥ 0.55；单次背景 ≥ 2；胜负分支可达率 100%；界面元素重叠 0。
3. 稳定性不倒退：check / 打包 / VM 通过率保持 100%，未知素材占比 ≤ 2%。
4. 成本可控：单次 ≤ 45 万 token、≤ 5 分钟；预算可按档位关闭。

### 非目标

- 不追求“任意需求都能做 3D/物理”，仍限定在 Scratch 2D 表达范围内。
- 不引入在线生图；素材仍来自官方库 + 外部 CC0 + 种子角色。
- 不改 GUI 交互主流程，只增加一个「高质量模式」开关与预算提示。

## 三、总体架构

```
用户需求
  │
  ├─ 0. 需求解析（轻）            core/intent.py（可选，先并入 planner）
  │
  ├─ 1. 设计文档 DesignSpec       core/planner.py         ← 新增
  │     主题 / 玩家动词 / 胜负 / 5~7 个 beat / 每幕素材短名单 / UI 安全区
  │
  ├─ 2. 视觉选角 Casting          core/casting.py         ← 新增
  │     每幕召回候选 → 缩略图给视觉模型 → 选出贴切且同系列的一组
  │
  ├─ 3. 分幕写脚本 BeatWriter     core/writer.py          ← 新增
  │     每幕独立调用，遵守统一接口契约（全局变量 / 广播 / 角色职责）
  │
  ├─ 4. 装配 Assembler            core/assembler.py       ← 新增
  │     合并分幕、补齐广播与变量、去重、注入素材、静态一致性校验
  │
  ├─ 5. 审稿 + 定向重写 Critic    core/critic.py          ← 新增
  │     评分表打分 → 只重写低分文件，最多 2 轮
  │
  ├─ 6. 试玩断言 Playtest         core/playtest.py + vm-runner/run.js 扩展
  │     脚本化点击/按键 30~60 秒，断言胜负可达、分数会变、无死循环
  │
  ├─ 7. 视觉/布局检查 VisualQA    core/layout_check.py（几何）+ visual_qa.py（可选像素）
  │
  └─ 8. 现有校验与打包            core/project.py（复用 check/lint/pack/VM）
```

每阶段都有独立输入输出与失败回退；任一阶段超预算或失败，降级到当前单轮流程，不阻塞出包。

### 新增模块与职责

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `core/planner.py` | 需求 → `DesignSpec`（JSON Schema 校验） | `assets_lib`、`storygen`、`schemas` |
| `core/casting.py` | 每幕素材召回 + 视觉重排 | `assets_lib`、视觉模型、缩略图 |

| `core/layout_check.py` | 目标框、出界、遮挡、UI 重叠的几何检查 | VM targets 数据、costume 尺寸 |
| `core/visual_qa.py` | 截帧 + 视觉判定（可选） | `sharp`、视觉模型 |

## 四、阶段详细设计

### A. 强制设计 + 分幕生成

**A1. 设计文档（planner）**

无论需求长短，高质量模式都先出一份 `DesignSpec`，字段固定：

```json
{
  "title": "森林找朋友",
  "theme": "动物/森林",
  "player_verb": "移动并点击",
  "win": {"type": "score", "target": 5},
  "lose": {"type": "time", "seconds": 30},
  "ui_safe_area": {"top": 60, "bottom": 60},
  "cast": [{"name": "cat", "role": "主角", "costume": "cat-a"}],
  "globals": ["score", "time_left", "playing"],
  "broadcasts": ["start_game", "game_over"],
  "beats": [
    {"id": "intro", "type": "intro", "goal": "交代目标",
     "backdrop": "Forest", "cast": ["cat"], "interaction": "none",
     "dialogue_beats": ["小猫想找朋友", "点击开始"]},
    {"id": "play", "type": "mini_game", "goal": "接住 5 个礼物",
     "backdrop": "Forest", "cast": ["cat", "gift"], "interaction": "click",
     "dialogue_beats": ["礼物出现了"]}
  ]
}
```

本地校验（`schemas` 扩展）：
- 必有 1 个 `intro`、1 个 `ending`；
- 每个 beat 必须有 `backdrop`、`cast`、`interaction`；
- `cast` 与 `globals`/`broadcasts` 必须闭包（引用都有定义）；
- 至少 2 种 interaction，游览类 ≥ 2 个 station；
- 所有素材名必须能在 catalog 解析，解析不了当场让模型改这一项。

**A2. 分幕生成（writer）**

每次只写一幕，带三样上下文：
1. 全局契约：变量表、广播表、角色职责表（谁移动、谁被点、谁说话）；
2. 本幕 beat：目标、背景、角色、交互、台词节拍；
3. 素材清单：本幕选中的造型文件名与尺寸。

输出仍是 `{"files": [...]}` 的补丁格式，复用现有 `validate_files`，但只校验本幕文件。失败只重写本幕，不重写全项目。

**A3. 装配（assembler）**

- 合并各幕补丁，同路径冲突时以“后幕追加脚本”为准；
- 检查每个 `broadcast` 有发送方和接收方，每个全局变量有初始化；
- 统一注入素材声明（复用 `assets.py`），避免每幕各声明一遍；
- 装配失败 → 回到 A2 只重写冲突的那一幕（最多 2 次）。

**A4. 接入点**

`build_scratch_project` 里在现有 `if _is_complex(...)` 处改为按 `QUALITY_MODE` 分流：
- `fast`：保持现状；
- `premium`：走 planner → casting → writer → assembler，再进入现有校验/打包/VM。

**预算**：设计 15k + 6 幕 × 20k + 装配 40k + 1 次重写 20k ≈ 195k（约 4.5 倍）。

**验收**：长需求（游览/剧情）后几幕的背景数、台词数不再明显低于前几幕；check/VM 通过率保持 100%。

---

### B. 审稿 + 候选挑选（best-of-2）

**B1. 评分表（critic）**

评分维度固定为 1~5，必须给证据（引用文件/行）：

| 维度 | 判断依据 |
| --- | --- |
| 可玩性 | 胜负条件是否明确、交互是否有反馈 |
| 编排完整 | 开场/过程/收尾是否齐、节奏是否塌 |
| 素材贴切 | 角色与背景是否符合主题 |
| 画面协调 | 是否同系列、尺寸是否合理 |
| 新颖度 | 是否只是模板套壳 |

自动信号（lint、VM、playtest、unknown）先算好，一起喂给 critic，避免“凭感觉打分”。

**B2. best-of-2**

同一 `DesignSpec` 生成 2 份完整工程，critic 各打一次总分，取高者；低分那份不丢弃，用于提取“差异点”生成重写指令。

**B3. 定向重写**

只对总分最低的 1~2 个维度重写对应文件，最多 2 轮；每轮重写后重跑 lint/VM，不通过则回滚到上一版。

**预算**：2 份基础（约 390k）+ 4 次 critic/重写（80k）≈ 470k，已接近上限，因此：
- best-of-2 只在 `premium` 开启；
- 分幕生成可先只生成 1 份，critic 低分时再补第 2 份（按需 best-of-2），把平均成本压到 300k 左右。

**验收**：同一需求 3 次生成的 critic 总分标准差下降 ≥ 30%；人工盲评最低分从 2 提升到 ≥ 3。

---

### C. 素材贴合与画面检查

**C1. 视觉选角（casting）**

1. 用现有 MMR 为每幕召回 12~20 个候选；
2. 取前 8 个缩略图（96×96 PNG）连同主题、beat 目标发给视觉模型，要求返回 `{pick: [名称], reject: [{名称, 原因}], series: "..."}`；
3. 本地校验：pick 必须在候选内、必须同系列优先、角色数不超过 beat 声明；
4. 失败回退到纯文本 MMR 结果。

> 说明：官方素材多为 PNG，可直接缩略；种子角色是 SVG，需要用 `sharp` 或预生成 PNG 缩略图。

**C2. 布局几何检查（layout_check，不依赖像素）**

基于 VM 导出的 targets（坐标、尺寸、可见性、造型）与 costume 的 `rotationCenter`：
- 角色是否出界（舞台 ±240/±180）；
- 角色是否过小（< 15% 舞台高）或过大（> 60%）；
- 顶部/底部 UI 安全区内是否有角色；
- 文字角色与可点角色是否重叠；
- 背景切换后角色是否仍在合理位置。

命中问题 → 直接生成确定性坐标修复，不经过 LLM，成本几乎为 0。

**C3. 截帧视觉检查（可选，第二阶段再做）**

把每个 target 的造型 SVG/PNG 按其坐标/缩放拼成一张 480×360 的 SVG，`sharp` 栅格化后发给视觉模型，检查“遮挡、风格冲突、可读性”，只输出建议，不直接改代码。

**预算**：视觉选角 6 × 8k = 48k；布局检查 0；截帧检查 2 帧 × 2 轮 ≈ 30k。

**验收**：出界/重叠类问题从“偶发”降到 0；人工“素材贴切”≥ 4/5。

---

### D. 试玩断言

**D1. run.js 扩展**

当前 `vm-runner/run.js` 已能点击所有可见角色、按方向键与空格、收集 say/broadcast/变量快照。扩展为接受试玩脚本：

```json
{"seconds": 45,
 "script": [
   {"t": 1.0, "action": "click", "target": "Start"},
   {"t": 2.0, "action": "key", "key": "ArrowRight", "hold": 1.5},
   {"t": 5.0, "action": "click", "target": "Gift1"}
 ]}
```

输出追加：`timeline`（每秒变量快照）、`stateCoverage`（是否到达 win/lose）、`stuckThreads`。

**D2. 断言（playtest.py）**

- 点击每个可点角色后，至少有一个变量/造型/位置发生变化；
- 运行 45 秒内到达 win 或 lose 之一；
- 分数变量单调变化（若定义为只增）；
- 无 `threadsRunning` 长期不降；
- 广播发送 ≥ 接收（没有无人接收的广播）。

失败项生成结构化 issue，交给 critic 做定向重写。

**预算**：20~30k（主要是失败后的修复调用）。

**验收**：5 个基准 prompt 胜负可达率 100%；“点了没反应”类人工反馈归零。

---

### E. 台词去模板化

- storygen 只负责**结构**（场景类型、节奏、交互种类），不再直接提供成句；
- 每幕台词由 writer 按角色“语气卡”（性格、口头禅、句长）生成 2~4 句；
- 生成后本地查重：连续 4 字以上重复、同一句式出现 > 2 次 → 让模型只重写这几句；
- 保留 Tracery 用于“表达方式”的多样性提示，不直接落文本。

**验收**：Distinct-2 ≥ 0.55，同一工程内重复句 ≤ 1。

## 五、成本与延迟模型

以当前单次 4.3 万 token / 101 秒为基线：

| 档位 | 组成 | token | 预估耗时 |
| --- | --- | --- | --- |
| fast（现状） | 单轮 + 校验 | 4.3 万 | 1.5~2 分钟 |
| premium-lite（A+E） | 设计 + 分幕 + 台词重写 | 20 万 | 3 分钟 |
| premium（A+B+C1+D+E） | 上述 + 视觉选角 + critic + 试玩 | 35~45 万 | 4~5 分钟 |
| premium-max（含 best-of-2 + 截帧） | 双候选 + 像素检查 | 70~90 万 | 7~10 分钟 |

分幕调用可并行（幕与幕之间无依赖），实际墙钟时间主要取决于最慢一幕与 critic 轮次。

预算闸门（`QUALITY_BUDGET`）：
- 单阶段超预算 → 跳过该阶段并记录；
- 总预算超限 → 停止 best-of-2 与额外重写，直接进入打包；
- 任何阶段失败 → 回退到当前单轮流程。

## 六、质量门槛与回归方法

沿用 `tools/ab_run.py`，新增一列 `premium` 版本做三方对比，固定 5 个基准 prompt（动物冒险 / 商场游览 / 餐厅经营 / 太空射击 / 校园故事）：

| 指标 | 门槛 |
| --- | --- |
| check + 打包 + VM 通过率 | 100% |
| 胜负可达率（playtest） | 100% |
| 点击有反馈率 | 100% |
| 单次背景数 | ≥ 2 |
| 角色造型数 | ≥ 5 |
| 台词 Distinct-2 | ≥ 0.55 |
| 未知素材占比 | ≤ 2% |
| 素材同系列比例 | ≥ 70% |
| 界面重叠 / 出界 | 0 |
| 人工盲评（4 维） | ≥ 4/5 |

人工盲评继续用现有模板，样本按 prompt 分组、新旧混合、不标版本。

## 七、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| token 成本失控 | 单次 10 倍甚至更多 | 阶段预算 + 总闸门 + best-of-2 按需触发 |
| 延迟变长 | 用户等待 5~10 分钟 | 分幕并行 + 流式进度 + 可随时停止 |
| 接口契约不一致 | 装配阶段冲突 | 契约先行 + 装配静态校验 + 只重写冲突幕 |
| 评分表过拟合 | critic 高分但人觉得一般 | 自动指标与人工盲评双轨，评分表随盲评结果迭代 |
| 视觉模型误判 | 选角反而变差 | 视觉只做重排与建议，最终仍受 catalog 与系列约束 |
| 引入渲染依赖 | 打包体积与兼容性 | 先做纯几何检查，像素渲染列为可选阶段 |
| 分幕导致“拼接感” | 幕间风格断裂 | 统一 DesignSpec + 同一素材池 + 装配时统一变量与转场 |

## 八、实施顺序

1. **A**：planner + writer + assembler，接入 `build_scratch_project`，跑现有 A/B 回归。
2. **E**：台词去模板化（可与 A 同批，改动集中在 writer 与 storygen）。

```json

  "quality_mode": "premium",
  "quality_budget": {
    "design": 15000,
    "beat": 20000,
    "critic": 20000,

    "visual": 30000,
```

- `best_of`：1 或 2；2 时按需降级；
- `visual_qa`：像素级检查开关，默认关闭；
- GUI 增加一个开关与“预计消耗”提示，不新增复杂设置页。

  写入 `config.json` 的 `quality_mode`；A/B 时也可用环境变量 `SCRATCH_QUALITY_MODE=premium` 临时切换。
- 没有任何「按需求长短自动开高质量」的隐式规则：开不开只看设置。
- 设计文档先校验再生成；不合法重试一次，仍失败自动回退单轮流程。
- 每幕独立请求，只允许写本幕角色；舞台由装配器确定性生成（全局变量、watch、背景声明、scene 切换）。
- 装配时自动给每个角色补 `when flag { hide; }`，避免所有角色先叠在舞台中心。
- 视觉选角把设计文档里已选素材 + MMR 备选缩略成 128×128 PNG（sharp 渲染 SVG/PNG），
  交给视觉模型判断贴切度与风格统一，只允许在候选名单内替换；`SCRATCH_CASTING=0` 可关闭。
- 分幕输出先做本地校验（路径归属、造型声明/引用一致、入口出口广播），不过关只重写本幕。
- 审稿评分 5 维（可玩性/编排/贴切/画面/新颖），只重写问题最集中的一幕；`SCRATCH_CRITIC=0` 可关闭。
- 试玩模式在交互冒烟后再跑 N 秒并采样舞台变量，只报结构性断点（点击无反应、游戏没开始、广播链断）。
- 布局检查用 targets 的坐标/尺寸做确定性判断：出界、过小/过大、多个可点角色叠在同一点。

### 11.2 实测（真实 LLM 生成）

### 11.3 已知限制

## 十二、长任务专项：购物中心 3 路线（2026-10-20）

### 12.1 问题复现

用课程作业同款需求跑了一次 premium（`course_mall`）：

- 结果是**线性 6 幕**（intro → beauty → food → quiz → sports → ending），没有 3 条可选路线；
- 没有 `route` 变量、没有路线调度，玩家点不出分支；
- 0 个音效、0 段音乐，`music_on` 是个死变量；
- 台词全中文（用户明确要求英文）；
- 台词总时长约 84 秒，离「≤5 分钟」很远，但也没有时长校验。

根因不是模型不会写，而是设计文档 schema 里**没有「路线」这个概念**，writer 只能按线性链生成；
音效也没有对应的 fractch 语法支持。

### 12.2 已落地的改动

**多路线**

- `DesignSpec` 新增 `routes` / `router_sprite`：
  `[{id, name, option_sprite, stations:[站id,...]}, ...]`，恰好 3 条、每条 2~3 站；
- `route_choice` 幕必须有 3 个选项角色 + 1 个调度角色；
- 选项点击：`if route == 0 { route = N; broadcast start_tour; }`，三块牌一起 `hide`；
- 调度角色：`when broadcast start_tour` 里按 route 依次 `broadcast_wait scene_<站>`，最后 `broadcast scene_<ending>`；
- 路线站禁止 `forever`（否则 `broadcast_wait` 永远不返回），互动用私有变量 + `until done == 1`；
- 装配层新增 `route_errors`：检查选项、隐藏、调度覆盖每一站、防连点；
- 修复 Stage 背景切换的去重 bug：相同背景在非相邻场景复用时，之前会漏掉切换。

**音频**

- 支持 fractch 的 `sound "Pop" file "assets/Pop.wav";` 与 `play_sound "Pop";`；
- 官方音效库（353 个）纳入 catalog 与 `@official:` 解析，程序自动补声明；
- 提示词要求：至少 1 段 BGM（`forever` + music 积木）和 2 处交互音效。

**长任务质量约束**

- 英文需求会显式传给 planner，台词/标题/注释强制英文；
- 每个角色文件必须写注释，每个 `when` 块前也要写；
- 生成后统计「台词句数/估算秒数/注释行数/BGM 是否循环/音效数」，超 5 分钟或缺音频会打印警告；
- 试玩新增二次点击（长开场后出现的选项也能点到），并避免把「开场还没播完」误判为游戏没启动。

### 12.3 实测（`course_mall4`）

| 指标 | 结果 |
| --- | --- |
| 结构 | 12 幕：intro + route_choice + 3 条路线 × 3 站 + ending |
| 规模 | 30 个角色，108 个文件 |
| 语言 | 81 句台词，中文 0 句；注释 83 行（英文） |
| 音频 | 32 处音效、6 段音乐积木 |
| 工程量 | 21 次 LLM 调用，382k token，554 秒 |
| 稳定性 | fractch check + 打包 + VM 通过 |
| 试玩 | 自动选中路线 3，广播到 `scene_sports_warmup` |

代价：382k token 约为 fast 基线的 8.8 倍，仍在 10 倍预算内；生成时间约 9 分钟。

### 12.4 还没解决

1. 无头试玩不会「玩」完一条路线：站内的按键/点击技巧它做不到，只能验证选路和广播链；
   真实可玩性仍需人工过一遍。
2. 108 个文件对 15 分钟演示偏重，建议人工删减到每路线 2 站、保留 1~2 个互动。
3. 个别角色仍会写错造型名/扩展名，靠本地校验重试拦下（会增加调用次数）。
4. 课程报告明确禁止 AI 生成，报告与 PPT 必须由小组自己写；本工具只负责 Scratch 工程。

## 十三、控制流改为装配器生成（2026-10-20）

### 13.1 目标

上一版虽然能生成 3 条路线，但 Router / 选项 / 站点入口仍是模型写的自由代码，
会出现「连点启动两条路线」「站点 forever 卡死调度器」这类状态机错误。
本阶段把**控制流从模型手里拿走**：模型只产出设计文档（台词、角色、素材），
代码由 `assembler.build_tour_project()` 确定性生成。

### 13.2 生成内容

多路线项目（`plan.routes` 非空）走新路径，不再调用逐幕 writer：

- **Stage**：背景声明、`route` / `done_*` / `hits_*` 全局变量、场景背景切换、`game_end`；
  `route` 强制初始化为 `0`（planner 写 `none` 也不会编译失败）。
- **Router**：`when broadcast start_tour` 里按 `route` 逐站
  `broadcast scene_<站>` + `wait_until done_<站> == 1`，最后 `scene_<ending>`。
- **选项**：三块牌显示/隐藏、`if route == 0` 防连点、点击后 `broadcast start_tour`。
- **站点**：按 interaction 选择固定模板：
  - `click`：宿主讲解后广播 `scene_<id>_play`，目标角色出现，点满 N 次置 `done_<id> = 1`；
  - `key`：宿主讲解后监听 `when key space`，按 3 次置 done；
  - `quiz`：宿主讲解后显示选项，点中 `correct` 置 done，点错只播 Lose；
  - `auto`：台词播完直接 done。
- **开场/结算**：自动播台词并广播下一幕/`game_end`。
- **MusicBox**：独立角色，`when flag { hide; forever { music...; wait } }`，全程循环 BGM。
- 所有生成文件带英文注释，并自动补 `when flag { hide; }`。

### 13.3 验收（自动跑三条路线）

`vm-runner/run.js` 新增 `routetest <route>` 模式：

- 提前把 `route` 设为指定路线，避免选项被连点；
- 主动广播 `start_tour`；
- 采样期间持续点击新出现的角色、持续按空格，模拟玩家把站内互动做完；
- 断言三条路线都必须出现 `game_end`。

`core/project.py` 在多路线项目打包后自动跑 3 条路线；失败只提示，
**不再让 LLM 改代码**（改只会破坏确定性状态机）。

### 13.4 实测

| 版本 | 调用 | token | 耗时 | 路线验收 |
| --- | --- | --- | --- | --- |
| 模型写控制流（course_mall4） | 21 | 382k | 554s | 只能到第 1 站 |
| 装配器生成（course_mall5） | 4 | 42.7k | 213s | 3/3 走到 game_end |

`course_mall5`：55 个文件、25 个角色、3 条路线 × 2 站，英文台词、循环 BGM、站点音效、
注释齐全；lint / fractch check / 打包 / 三条路线试玩全部通过。

### 13.5 代价与后续

- 内容量下降：站点台词只来自 planner 的 1~4 句，不再有逐幕 writer 扩写。
- 互动形式固定为点击/按键/答题三种模板，变化来自素材、台词和站点数量。
- 后续如需更丰富的文案，可加一个**只输出台词/提示文本**的 content 环节，
  仍然不碰控制流；这样既保留确定性，又能恢复文案厚度。
